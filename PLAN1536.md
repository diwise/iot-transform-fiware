# PLAN1536 — Kodändringar Etapp 8 (inga mall-/regeländringar)

## Syfte och avgränsning

Fokusera enbart på kodändringar/kodförbättringar i `iot-transform-fiware`.
Befintliga mallar och regler (`deployments/models/*.yaml`, seed-innehåll,
modelltester) rörs inte — samtliga mallar/regeler görs om när regelmotorn är klar.

Motorn får inga modellnamn eller modellspecialfall. Standardreglernas
modellval stannar i regelfiler.

Berör `TRANSFORM.md:709-727` (Etapp 8), exklusive rena regel-/dokumentationspunkter.

## Utgångsläge

- `internal/presentation/api/preview.go:35-57,91-129,161-255`: offline-preview med
  inline-regel, generisk `skippedReason`, `operation/context` finns men
  `removeAttributes`-lista, precis orsak och effektiv-vs-fallback-context saknas.
  Fel från transform returneras rått.
- `internal/application/transform/diagnostics.go:15-60`: `ExplainMatch` /
  `PotentialOverlaps` finns, används bara i `internal/presentation/api/snapshot.go:88`
  (debug-logg). Preview använder det inte.
- `internal/presentation/messaging/things/relations.go:23-84`: stateless —
  ett event ger `Transform` och `ApplyEntityWrites`. Ingen projektion,
  ingen mängdhantering, ingen bootstrap.
- `internal/infrastructure/rules/postgres.go` + `migrations/`: endast
  `transform_rules` + version. Ingen relationstabell.
- `internal/presentation/api/register.go:196-211`: `writeAPIError` mappar
  validering/not-found/konflikt, övrigt blir generisk `500`.
- `internal/presentation/messaging/delivery.go:22-30`: `DataError` ger
  `Permanent`, `DependencyError` skiljer permanent brokerfel från tillfälligt.
- `assets/docs/openapi.yaml:/models/preview`: beskriver `matched/entities/observations`
  men inte rensade attribut, effektiv context-källa eller strukturerade orsaker.

## Fas A — Preview: konkret utfall + precisa orsaker + felklassificering

Motsvarar `TRANSFORM.md:717-718` + `724-725`.

1. Utöka svarskontraktet i `internal/presentation/api/preview.go`:
   - `removeAttributes: []string` per entitet.
   - `effectiveContext` + `contextSource: rule|fallback`.
   - Strukturerad `skip/valideringsorsak {kod, regel, entitet, attribut, uttryck}`
     i stället för fri `skippedReason`-sträng.
   - Uppdatera `assets/docs/openapi.yaml` (`/models/preview`) i samma ändring.
2. Klassificera fel i `previewModel` / `previewTransform` + `writeAPIError`:
   - Regel-/exempeldatafel ger `400` med ovanstående kontext, aldrig `500`
     eller generisk `internal error`.
   - Beroendefel (t.ex. fallback-context) förblir server-/beroendefel.
   - Behåll offline-garantin: aldrig broker-kontakt, aldrig persistens.
3. Tester: nya fall i `internal/presentation/api` för `remove`, `delete`,
   `required`-suppress, ogiltig NGSI-LD-utdata, tom context mot fallback.
   Kontrollera faktisk JSON, inte bara att dekoratör skapades.

## Fas C — Diagnostik mot aktiv snapshot

Motsvarar `TRANSFORM.md:719-720`.

1. Ny läs-endpoint (förslag `POST /models/preview/explain`, alternativt

   - Output: `snapshotVersion`, vald regel `{id, revision, priority,

   - Återanvänd `Snapshot()` + `ExplainMatch`. Ingen ny matchlogik.

3. Tester: prioritet/specificitet/ordning, tenant-isolering

## Fas D — Relationsprojektion växthus/tank-mängd

Motsvarar `TRANSFORM.md:709-714`. Största posten.
Modellneutral, tenant-isolerad. Inga tank-/växthusnamn i kod.

1. Design (kort, före kod):
   - Tabell `relation_projection(tenant, relation, from_id, to_id, revision,
     removed, updated_at)` med unik `(tenant, relation, from_id, to_id)`.
   - En rad per källrelation, inte färdiga FIWARE-ID:n.
2. Migration + store:
   - Ny migration under `internal/infrastructure/rules/migrations/`.
   - Nytt `ProjectionStore` med `ctx` överallt, parametriserad SQL,
     `pgx.ErrNoRows` mot domänfel, transaktion per delta.
3. Handler-logik i `presentation/messaging/things/relations.go`
   (eller ny `application/relations`-service injicerad via konstruktor):
   - `set`: upsert + bygg komplett mål-mängd för berört `to`.
   - `remove`/flytt: ta bort + bygg mängd för både nytt och tidigare mål.
   - Skriv mängden som `Relationship array:true` via befintlig motor och
     `ApplyEntityWrites`. Redan lyckade brokerskrivningar bevaras i
     felrapport; brokerfel ger temporary (replay från början, idempotent).
4. Robusthet:
   - Samtidig mutation via DB-transaktion (ingen mutex-garanti mellan instanser).
   - Omstart: bygg från DB, ingen minnes-state.
   - Bootstrap/återsynk för befintliga relationer (endpoint eller startjobb).
   - Cancellation/timeout via request-`ctx`.
5. Tester: transaktion/konkurrens (`-race`), brokerfel/replay med kontrollerad
   HTTP-server, omstart, bootstrap, tenant-isolering. Isolerad PG, `-count=1`,
   verifiera att tester ej skippas.

## Förhållande till PLAN1050 J2/K (synk, inga avbockningar)

POI-beskrivning/Point-Polygon/tidskällor/enheter) är utförd under PLAN1050
J2 med modelltester (`internal/infrastructure/config/j2_standard_test.go`):
POI-beskrivning från `metadata.description`, plats via `field: geometry`
(Point/Polygon/3D), `dateObserved` = max-observedAt, Sewer kräver plats/tid
med dokumenterade `overflowTime`/`refDevice`-avsteg, greenhouse/tank-regler
förblir borttagna. Kodpunkterna ovan (Fas A–D) och deras boxar är opåverkade
av J2 och bockas inte av här utan den verifiering de kräver.
